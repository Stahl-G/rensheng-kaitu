# 多 Agent 开发流程（提案）

更新：2026-10-18。待用户决定，未生效。
对照的方案：pstack 双角色方案（Codex 整理，上游固定在 `cursor/plugins@ad26795`）；另一份方案（sinatra）还没看到，看到后补对照。

## 1. 仓库现状（2026-10-18 核对）

- **没有 CI。** 仓库没有 `.github/workflows`，PR 上没有任何检查。唯一自动跑的是 Codex 的 PR 审查机器人，它只读 diff，不跑产品。
- **main 没有保护。** 不少提交直接推到 main，不经 PR：10-17 的版本发布、功能和本地合并都是这样，10-18 还有 `2d88323`。
- **所有 Agent 共用一个 GitHub 账号。** PR 作者和合并人都是 Stahl-G。GitHub 不允许作者批准自己的 PR，所以「要求批准」这条用不上，只能靠检查状态。
- **仓库是公开的。** 分支保护和 GitHub Actions 都免费，包括 macOS 和 Windows 机器。
- **安全：** 10-16 两轮审查（P1、P2、SEC-01 到 SEC-09）已在 main 修复（`92dcdc0`），有回归测试，见 `docs/acceptance/security-remediation-2026-10-16.md`。
- **已有的基础：**
  - `pnpm lint`、`build`、`typecheck`、`test` 在 Linux 上都能跑。root 身份下 `status.test.ts` 有一条已知失败，CI 不用 root，不受影响。
  - 隔离用的环境变量：`KAITU_DIR`、`KAITU_APP_HOME`、`KAITU_LOCAL_STATE_DIR`、`HOME`。
  - 合成大工作区的测速脚本 `scripts/measure-phone-sync.mjs`。
  - 监管 Agent 已经在做非作者复查。

这一轮实际出过的问题：

1. **两个会话的要求打架。** 监管要求保留旧版手机操作账本的兼容代码，另一个会话把它删了。缺一个大家都查的决定记录。
2. **检查顺序不固定。** core 的 `dist` 过期，DSH 插件的 typecheck 就报假错，要先 build 再 typecheck。
3. **碰真实资料的代码没人实跑。** PR #15 操作日历 App 的脚本没有运行过，因为跑了会改用户真实的日历。
4. **机器审查有用，但不够。** Codex 机器人在 PR #15 提的 P1 是真问题；但它不运行产品，替代不了实跑。

## 2. 对 pstack 方案的评价

方向对，核心几条应该保留：

- 非作者验收；
- 结论跟着提交走；
- 按真实用户路径实跑；
- CI 全绿不等于可以合并；
- 合并和发布由人决定。

按开图的现状，有五处要改：

1. **漏了最便宜的一层。** 方案引用的四层（工程结构 > 测试和 CI > 文字规则 > 人工逐个审）把 CI 放在文字规则前面，但方案主体是文字规则和人工记录，仓库却连 CI 都没有。应该先上 CI 和 main 保护。
2. **太重。** 它要求：
   - 每个 PR 一个审计目录和决定日志；
   - 结论键由六项组成，手工维护；
   - 每个 PR 都开 base 和 head 两个工作树；
   - 只改文档也要非作者重新验收；
   - 结论分五种。

   单人项目、10-22 要交 TestFlight，这套流程会拖慢速度，最后没人照做。
3. **「结论绑定提交」不必手工记。** 把验收结论写成 GitHub 的提交状态即可：新提交上自然没有这个状态，分支保护会挡住合并。
4. **没有分风险。** 开图有明确的高风险类：数据规范、隐私和安全边界、同步和迁移、写系统日历、健康数据和 iCloud、凭据。AGENTS.md 已经规定数据规范要用户点头。文案、样式、文档不该和这些走一样的流程。
5. **没有能实跑的验收环境。** 开图会写真实的日历、iCloud 和健康数据。「独立实跑」需要一个不碰用户资料的地方，否则还会出现 PR #15 那种「脚本没实跑」。

方案对共用账号的分析是对的：两个会话用同一个账号，在 GitHub 看来就是同一个人。由此得出的做法也对：不靠 GitHub 的批准，靠检查状态。

## 3. 建议的流程

### 3.1 角色

| 角色 | 谁 | 做什么 | 不做什么 |
|---|---|---|---|
| 用户 | 你 | 定任务队列和先后；数据规范、隐私、发布的决定；合并（或授权某个 Agent 合并全绿的 PR） | |
| 开发 | Codex 为主；Claude Code、CodeBuddy、Cursor 等做并行任务 | 一个任务一个分支、一个工作树；早开 PR；自己跑检查；PR 说明写清怎么验证、哪里没验证 | 不写自己 PR 的验收结论；不直接推 main |
| 验收 | 和作者不同家的 Agent（Codex 写的由 Claude Code 验，反过来也一样）；监管 Agent 可以兼任 | 在 head 提交上另开工作树和独立环境，按任务原文实跑，写结论 | 不改产品代码；发现问题退回开发 |
| 机器 | GitHub Actions；Codex 审查机器人 | lint、build、typecheck、test；审 diff | |

### 3.2 风险分级

| 级别 | 范围 | 合并条件 |
|---|---|---|
| 轻 | 文档、文案、样式、只加测试 | CI 绿；Codex 机器人的意见看过 |
| 普通 | 功能、bug 修复 | CI 绿 + 非作者验收通过 |
| 重 | `schemas/` 和 PRD §6、AGENTS.md 生成模板、隐私和安全边界、同步/迁移/备份、写系统日历/健康/iCloud、凭据、发布打包 | CI 绿 + 非作者验收（必须实跑相关路径）+ 用户在 PR 上明确同意 |

- 级别用 PR 标签标出：`risk:light`、`risk:normal`、`risk:high`。
- 改到上面「重」级路径的 PR，CI 自动标 `risk:high`，开发不能自己降级。

### 3.3 一个 PR 的流程

1. **任务卡。** 写清一句话目标、完成标准、允许改的范围、风险级别。放 GitHub issue 或交接文档。
2. **开发。**
   - 从最新 main 开分支，早开 draft PR。
   - 写完自测：`pnpm lint && pnpm build && pnpm typecheck && pnpm test`。AGENTS.md 要求的耗时，在合成大工作区上实测。
   - 转为 ready。说明里写：改了什么、从哪个入口验证、实测耗时、没验证的部分。
3. **CI 自动跑。** 红了由开发修。
4. **验收（普通、重级）。**
   - 在 head 提交上另开工作树。环境变量指向临时目录，不碰真实工作区。
   - 读任务原文和 diff，走一遍受影响的用户路径，确认 Codex 机器人的意见已处理。
   - 通过：在这个提交上写状态 `kaitu/acceptance = success`，PR 留言附证据（命令输出、截图位置）。
   - 不通过：留言写问题和复现步骤，状态写 `failure`，退回开发。
5. **有了新提交。** 旧状态不再对新提交有效。
   - 只改了文档，或只修了验收提的问题：验收看增量 diff（`git diff 旧提交..新提交`），没问题就直接重写 success。
   - 改了逻辑：重跑受影响的路径。
6. **合并。**
   - 最新提交上 CI 和验收状态都绿，重级再加用户同意，才能合并。
   - 初期由用户按按钮，或授权一个 Agent 合并；不开自动合并。
   - 合并不等于发布，发版另外做。

写状态的命令：

```bash
gh api repos/Stahl-G/rensheng-kaitu/statuses/<head SHA> \
  -f state=success -f context=kaitu/acceptance -f description="验收通过：<一句话>"
```

### 3.4 先建的基础设施（按顺序）

1. **CI。**
   - GitHub Actions，Ubuntu，Node 22，pnpm 11。
   - 依次：`pnpm install --frozen-lockfile` → lint → build → typecheck → test。build 放在 typecheck 前，避免 dist 过期的假失败。
   - 用 `pull_request` 触发，不用 `pull_request_target`。公开仓库收到外部 PR 时，这样不会把写权限交给外部代码。
   - macOS 和 Windows 的机器免费，跑顺后可以加上。
2. **main 保护。**
   - 必须走 PR，必须 CI 通过。
   - 验收状态等流程跑顺后再设为必须。
   - 对管理员也生效，不留绕过。所有 Agent 用的都是你的账号，给管理员留绕过就等于给每个 Agent 留了绕过，挡不住直接推 main。
   - 真要紧急发布，你在网页上临时关掉保护，发完再打开。
3. **决定记录。**
   - HANDOFF 的决定表（D1 起）作为唯一来源。
   - 推翻已有决定或监管要求的 PR，说明里必须写推翻哪条、谁同意的。旧账本那次就缺这条。
4. **验收工具包。**
   - **合成工作区脚本：** 生成大工作区和典型资料，复用 `measure-phone-sync.mjs` 的隔离环境变量。
   - **功能地图：** 先写五个——今天、开图（进度图）、资料、问问、手机同步。每个写：
     - 入口；
     - 怎么驱动（CLI 命令，或浏览器打开 `kaitu ui` 后点哪里）；
     - 容易出错的地方。
   - **假 AI 服务商：** 问问用固定回答，不花钱，结果可重复。
   - **macOS 专属路径（系统日历、iCloud、健康）：** 在 Mac 上建一个不登录用户 iCloud 的测试账户，或给日历名加测试开关（例如 `KAITU_CALENDAR_NAME`），验收在那里实跑。
   - **iOS 仓库：** 解码测试固定用本仓库某个提交的 `schemas/fixtures/phone/`。

### 3.5 推行节奏

- **现在到 10-23：** 只做 §3.4 第 1、2 条（CI 和 main 走 PR），半天以内。不加人工流程，免得拖发布。
- **发布后第一周：**
  - 开始非作者验收，先用在重级 PR。
  - 写功能地图和合成工作区脚本。
- **两到三周后看数据：**
  - 看什么：漏进 main 的问题、退回次数、每个 PR 的等待时间。
  - 再决定：验收状态是否设为必须；是否扩大到普通级；是否授权 Agent 合并全绿的 PR。

### 3.6 从 pstack 方案保留和去掉的

- **保留：**
  - 非作者验收、结论跟提交走、实跑用户路径；
  - CI 全绿不等于可以合并；
  - 问题退回作者修；
  - 一个分支只有一个写入者；
  - 用户说停就全停；
  - main 上本来就有的问题单列，不算到 PR 头上。
- **去掉或推迟：**
  - 审计目录和决定日志；
  - 手工维护的结论键，改用提交状态；
  - 每个 PR 都开 base 和 head 两个工作树，只在修 bug、需要先在 main 上复现时才开；
  - 文档改动也全量重验；
  - 一个 PR 配多个验收实例；
  - BLOCKED、INCONCLUSIVE 两种结论，统一写 failure 并写明原因；
  - 上游的 PR 监视脚本。方案自己也发现，它不把「还需要审查批准」当作阻断。
