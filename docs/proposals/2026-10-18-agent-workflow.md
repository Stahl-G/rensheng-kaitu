## 1. 仓库现状（2026-10-18 核对）

B 第 1 节的事实我逐条核对过，都对：

- **没有 CI，main 没有保护。** 仓库没有 `.github/`；main 的 `protected` 为 false。
- **直接推 main。** 很多提交不经 PR，包括 10-17 的版本发布，10-18 还有 `2d88323`。
- **两个高危安全问题已修。** 一个是自定义模块读记录越界（P1-1 / SEC-06），一个是内置 AI 能读到密钥（P1-2 / SEC-03）。修复在 `92dcdc0`（10-16 14:27，越南时间），回归测试是 `packages/core/test/security-records.test.ts` 和 `packages/cli/test/security-state.test.ts`。
- **隐私。** 私有项目在 `d00584f`（10-16 17:15）整体删除。现在只剩记忆的 sensitive 标记，远程 MCP 读不到标了它的记忆。
- **规模。** 87 个测试文件，`packages/web` 没有测试；AGENTS.md 16 行。

B 没提到、但影响方案的三点：

- **所有 Agent 共用你的 GitHub 账号。** PR 作者和合并人都是 Stahl-G。GitHub 不允许作者批准自己的 PR，「要求批准」用不上。
- **管理员能绕过分支保护，你的 `gh` 登录还能改仓库设置。** Agent 用的是你的身份，所以「Agent 不改仓库设置」只是文字约定，挡不住。
- **仓库是公开的。** 分支保护和 GitHub Actions 都免费，macOS、Windows 的机器也免费。

**本地模拟 CI。** 在 `d48c52a` 的干净副本上跑，环境是 Linux、Node 22、pnpm 11：

| 步骤 | 结果 | 用时 |
|---|---|---|
| `pnpm install --frozen-lockfile` | 通过 | 7 秒（有缓存） |
| 不先 build 直接 `pnpm typecheck` | 失败：`packages/channels` 找不到 `@kaitu/core`，和 B 说的一致 | 11 秒 |
| `pnpm build` | 通过，包括 DSH 插件 | 28 秒 |
| `pnpm typecheck` | 通过 | 20 秒 |

全程约三分半。B 担心的「DSH 插件在 CI 上构建不了」不成立。

**这一轮实际出过的问题：**

1. **两个会话的要求打架。** 监管要求保留旧版手机操作账本的兼容代码，另一个会话把它删了。A 和 B 都没防这个。
2. **检查顺序不固定。** 不先 build 就 typecheck 会报假错，上面已经复现。
3. **碰真实资料的代码没人实跑。** PR #15 操作日历 App 的脚本没有运行过，因为跑了会改你真实的日历。
4. **机器审查有用，但不够。** Codex 的 PR 审查机器人在 PR #15 提出的 P1 是真问题，但它只读 diff，不跑产品。

## 2. 两份方案的评价

### A：提醒有价值，做法太重

- **对的地方：**
  - 非作者验收；
  - 结论跟着提交走；
  - 用真实用户路径实跑；
  - 指出同一个 GitHub 账号在平台上就是同一个人；
  - 指出工作树不是沙箱，端口、数据目录、模拟器要各自独立；
  - 指出合并可能触发发布。
- **问题：**
  - **没对照仓库**，写的时候目标仓库都没定，所以没有 CI 方案，也没有具体路径。
  - **记账太多：**每个 PR 一个审计目录和决定日志、手工维护的结论键、每个 PR 开两个工作树、只改文档也要换人重验。

### B：底本，有六处要改

B 贴着仓库写：有真实路径和命令、按阶段推进、有毕业条件，也有「第二次犯就写成规则」。要改的是：

1. **时间撞上发布。** 第 0 阶段排在 10-19 到 10-21，第一个验证任务排在 10-22，正是 TestFlight 那天。发布前只该做 CI 和分支保护。确认 Cursor CLI 的能力、装 pstack、写验证技能，都放到 10-23 之后。
2. **夜里无人值守的安全边界没写。**
   - 在你 Mac 上跑的 Agent 用的是你的系统账户，能碰到真实工作区、日历、钥匙串和 `gh` 登录。B 隔离了 HOME，但隔离不了日历 App。
   - 夜间运行要么放在云端会话（独立容器，碰不到你的资料），要么放在 Mac 上一个不登录你 iCloud 的测试账户里。
3. **「验证通过」不该用标签记。** 推了新提交，`verify:pass` 标签还挂着，旧的通过会被当成新的。
   - 改成在那个提交上写 GitHub 提交状态 `kaitu/verify`：新提交上没有这个状态，分支保护会挡住合并。
   - PR 描述里的验证结论保留，作为证据。
4. **「Agent 不改仓库设置」要变成结构。**
   - 分支保护对管理员也生效，不留绕过。
   - Agent 用专门的细粒度 token，只给内容、PR、提交状态的读写，不给管理权限。这样它既推不了 main，也关不掉保护。
   - 紧急发布时，你在网页上临时关掉保护，发完再打开。
5. **主控不要依赖 Cursor 专有功能。**
   - B 的主控靠 Cursor CLI 加 pstack 的 `/poteto-mode`、`/loop` 和云端子智能体，这几样它自己标了【未核实】。A 还指出，`poteto-mode` 默认的自主范围比你给的边界宽。
   - 关卡应该放在 CI、提交状态和分支保护上，用什么工具都一样。pstack 的流程文档只作参考，不作为依赖安装。
6. **风险分级有缺口，毕业的回报也小。**
   - **缺口：**R0「只改 docs/」漏了这几处，都应划进 R3：
     - PRD §6（数据规范，AGENTS.md 第 2 条要你确认）；
     - `docs/guides/phone-contract.md`（手机读写格式）；
     - AGENTS.md 和 CLAUDE.md（改 Agent 规则就是改关卡）。
   - **回报：**按 B 的红线表近似匹配，回看 10-12 以来 main 上的 182 个提交：
     - 106 个（58%）碰到 R3，另有 17 个只碰 R2；
     - 毕业后能自动合并的不到三分之一（59 个，其中 25 个只改文档）；
     - 只保护密钥、文件权限、MCP 远程范围、隐私页、数据规范、发布、依赖和检查本身，也还有 71 个（39%）。

     这段时间在改数据规范和手机契约，R3 多是正常的。
   - **所以：**毕业那套（20 个 PR、两周指标、每周报告）先不用做重；更值得做的是让 R3 审得快，一份影响说明加验证者的实跑截图，两分钟能定。

小问题：

- **重验规则有一条落空。** B 的 7.4 允许只改 lint 配置时沿用旧结论，但 `biome.json` 又在 R3 里，按它自己的规则要重验，这一条等于作废。统一按 §3.3 第 5 步处理。
- **指标不用手写。** 每周指标从 PR 标签和提交状态用脚本算，不往 `docs/acceptance/` 写周报。

## 3. 合并后的方案

### 3.1 角色

| 角色 | 谁 | 做什么 | 不做什么 |
|---|---|---|---|
| 操作者 | dot | 定方向、批任务、合并（stack 阶段全部由你合并）、回答 R3 的影响说明 | |
| 派单和汇总 | 白天由现在的监管 Agent 兼任；Grok Bot 负责 07:30 汇总和转达「停」 | 写任务单、派负责人和验证者、汇总结论、给放宽检查的改动复签 | 不写代码、不合并 |
| 负责人 | Codex、Claude Code、Cursor、CodeBuddy 都可以；一个 PR 一个 | 写代码、早开 PR、自测、按结论修、每个新提交都报 | 不给自己验证；不推别人的分支；不推 main |
| 验证者 | 没参与写这份代码、最好换一家的会话；能用云端会话就用云端 | 三条验证线（B 的 7.2），写提交状态和结论 | 不推修复 |
| 机器 | GitHub Actions；Codex 审查机器人 | CI 必须通过的检查；每个 PR 的 diff 审查 | |

暂不设常驻的夜间主控。每批最多 3 个 PR（照 B）。

### 3.2 风险分级

用 B 的 R0 到 R3 和路径表，改三处：

- **R0 只限说明性文档。** PRD §6、`docs/guides/phone-contract.md`、`docs/site/privacy*`、AGENTS.md、CLAUDE.md 划进 R3。
- **R2 先由人合并。** 毕业评审时和 R1 一起评估，不定成「永远」。
- **等级由 `scripts/risk-class.mjs` 按 diff 算，自动打标签。** CI 检查标签不低于算出来的等级；这张路径表本身属于 R3。

### 3.3 一个 PR 的流程

1. **任务单。** 用 B 5.1 的格式，放 GitHub issue。
2. **负责人开发。**
   - 从最新 main 开分支，早开 draft PR。
   - 自测：`pnpm install --frozen-lockfile && pnpm build && pnpm lint && pnpm typecheck && pnpm test`，build 必须在 typecheck 前。
   - PR 描述按 B 5.3 的四节写。另外：
     - 推翻已有决定或监管要求的，写明推翻哪条、谁同意的；
     - 碰真实资料的部分，写明怎么在测试环境实跑。
3. **CI 自动跑。** 红了由负责人修。
4. **验证。**
   - 验证者在 head 提交上另开环境：`KAITU_DIR`、`KAITU_APP_HOME`、`KAITU_LOCAL_STATE_DIR`、`HOME` 都指向临时目录。
   - 走 B 7.2 的三条线：重跑检查、真界面操作、对抗审查 diff。
   - 通过：写提交状态，结论按 B 7.3 的格式写进 PR。
     ```bash
     gh api repos/Stahl-G/rensheng-kaitu/statuses/<head SHA> \
       -f state=success -f context=kaitu/verify -f description="PASS：<一句话>"
     ```
   - 发现问题：状态写 `failure`，一次列全，退回负责人。
5. **有了新提交。** 旧状态不再对新提交有效。
   - 只修了验证提的问题，或只改了说明文字：验证者看增量 diff（`git diff 旧提交..新提交`），没问题就重写状态。
   - 改了逻辑，或碰到 R3：重跑受影响的路径。
6. **合并。**
   - stack 阶段由你合并。条件：最新提交上 CI 和 `kaitu/verify` 都是绿的；R3 再加你读过影响说明。
   - 不开自动合并；合并不等于发布。

### 3.4 要先建的东西（按顺序）

1. **CI。**
   - B 第 8 节的 `ci.yml` 照写：`pull_request` 和 push 到 main 时触发，Node 22，pnpm 11.22.0。
   - 用 `pull_request` 触发，不用 `pull_request_target`。公开仓库收到外部 PR 时，这样不会把写权限交给外部代码。
2. **分支保护和 Agent 的 token。**
   - 你在设置里开：必须走 PR、必须通过 CI、不许强推、不许删除、对管理员也生效。
   - 给 Agent 换成没有管理权限的细粒度 token。
3. **`kaitu/verify` 提交状态。** 流程跑顺几个 PR 后，再设为分支保护的必须项。
4. **`risk-class.mjs` 和 CI 里的 no-skip 检查。** 不许新增 `.skip` / `.only`，照 B。
5. **验证技能 `verify-kaitu`。**
   - **内容：**照 B 7.1 写 Launch、Doctor、Drive、Evidence、Cleanup。启动 `kaitu ui --no-open`，端口 4870；MCP 冒烟用 `kaitu mcp --http --port 4871 --tools remote` 和 `kaitu mcp token`。这些命令我都核对过。
   - **放在哪：**放在所有工具都读得到的位置，从 AGENTS.md 链接过去，不只放 `.cursor/skills/`。
   - **功能地图：**第一批里至少有一条开图本身的流程，例如今天页记一条，或手机收件箱处理，不只做官网 FAQ。
   - **问问：**用假的 AI 服务商，固定回答。
   - **macOS 专属路径（日历、iCloud、健康）：**只在 Mac 的测试账户里跑；日历名留一个测试开关，绝不对你的真实日历运行。
6. **决定记录。** HANDOFF 的决定表作为跨 PR 决定的唯一来源；单个 PR 的决定写在 PR 描述里，不建 `.audit/`。

## 4. 对 B 第 12 节问题的回答

1. **主控放哪？**
   - stack 阶段不设常驻主控：白天派单和汇总由现在的监管 Agent 兼任。
   - Grok Bot 做 07:30 汇总和转达「停」。它每条命令都要人批准，不适合夜里跑，同意 B 的判断。
   - 夜间无人值守等第 1 阶段跑顺，而且只在碰不到你资料的环境里跑。
2. **四种工具能混用吗？** 能。关卡在 CI、提交状态和分支保护上，跟工具无关；混用正好满足「换一家验证」。不依赖 `/loop` 和 Cursor 子智能体。
3. **验证者用几个？**
   - R1 一个，必须换一家。
   - R3 一个，重点做对抗审查；安全、隐私、数据迁移类再加一个。
   - Codex 审查机器人已经在每个 PR 上审一遍 diff，算半个第二验证者。
4. **dsh-plugin 在 CI 上构建不了怎么办？** 实测能构建（见 §1），不用拆。同意底线：不设「失败也放行」。
5. **「不发给 AI」开关怎么实现？** 分两类出口：
   - **经过开图的出口，在 core 统一拦截就够。**包括：
     - 内置 AI：文件和搜索都走 `agent-file-policy.ts`，就是 SEC-03 修好的那个统一入口；
     - MCP 远程工具：照 sensitive 记忆的过滤方式；
     - 近况资料包；
     - 手机快照；
     - 每日整理：整理靠内置 AI，读不到也就摘不进 handoffs 和 feed。

     要求是一个判断函数、所有出口共用。
   - **不经过开图、直接读文件的出口，开图拦不住。**
     - 连了 Google Drive 的 Grok、ChatGPT：Drive 模式下整个 kaitu 文件夹都在 Drive 里，它们能读到同步文件夹里的一切。
     - 本机直接读磁盘的 Claude Code、Codex。

     这类只能靠两样：AGENTS.md 写明要求，界面上如实说「这个开关管不住直接读你云盘或磁盘的 AI」。iCloud 模式没有云端接力，不受这条影响。
   - **开关本身只有你能关。**Agent 想改，在写入入口就拒绝。
   - **它是新的配置字段。**按 AGENTS.md 第 2 条，先定规范，再同步改 `schemas/` 和模板。
6. **gh-pages 要不要进流程？**
   - 发布前不改。
   - 推送前用真浏览器打开核对，就是 `verify-kaitu` 的 FAQ 用例。
   - 改下载链接、「已签名」、隐私说明、版本状态的，要你点头。
   - 发布后再考虑改成从 main 的源码生成。
7. **R2 永远人工合并会不会太保守？** 会。界面改动能撤回，靠带截图的实跑把关。毕业前由人合，毕业时和 R1 一起评估。
8. **决策记录放哪？** 单个 PR 的放 PR 描述；跨 PR 的产品决定进 HANDOFF 决定表。不建 `.audit/`。
9. **早间 15 到 30 分钟现实吗？**
   - 每批不超过 3 个 PR、证据齐全的话现实。
   - 抽查 main 不必每天固定做：有合并的第二天查，R3 合并后必查。
