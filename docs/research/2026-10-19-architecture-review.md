# 「开图 2.0 架构演进」调研报告的评估

更新：2026-10-19。评估对象：用户的 Gemini 产品经理写的《开图 (Kaitu) 2.0 架构演进与技术壁垒综合调研报告》（Google 文档）。站在架构的角度判断哪些值得引入；依据是当前代码（`claude/product-analysis-north-star-z6g5gu`）、[launch.md](../prd/launch.md) §1a 的定位和四道门槛，以及已定的产品原则。

## 结论

报告指出的病症有一半成立，开出的药方大多不适合现在。值得引入的是下面四项，都要先缩到最小版本：

| # | 项目 | 判断 | 代价 | 要不要用户点头 |
|---|---|---|---|---|
| 1 | 出口统一过滤 | 引入，先做 | 约 1 天 | GitHub 备份的口径要定（见 1.4） |
| 2 | 趋势体重 | 引入 | 半天 | 只在电脑上显示不用；进手机快照要改格式 |
| 3 | 记忆的「已结束 / 被替换」 | 引入 | 约 1 天 | 要（数据规范改动） |
| 4 | 夜间整理多做三件事 | 引入，当规则升级做 | 约 1 天 | 规则版本从 1 升到 2 |

其余提议（动态 TDEE、训练准备度、双时态图谱和 PageRank、技能自演化、潘多拉魔盒指数、信念依赖图、因果扫描、节律调度）暂不引入，理由见文末。

### 报告的前提有几处过时或冲突

- 它描述的是早期 PRD：「今天 / 健康 / 动态 / 我的」四个视图、照访谈复刻的首屏、`local_only` 项目。代码里已经没有 `local_only`，首屏和愿景页 10-18 已经改成「一个人、一个 AI、一件长期的事」。
- 和已定的决定冲突：
  - 完成率曲线「只算按计划做到的比例，不算效果、不下因果结论」（2026-10-17）。报告的「因果发现卡」「p=0.04」正好相反。
  - 产品原则「不催、不做每日打分」。报告的主动干预和按警觉度改任务正好相反。
  - 「G3 记录可靠优先于任何新模块」。报告要加四个新引擎。
- 引用里有几处核对不了（期刊卷号和年份不一致、个别 arXiv 编号）。对外引用前逐条核实。

报告里真正有用的一句话是：**数字由代码算，AI 只写话。** 让模型直接读原始流水账去算数，既不准也不稳。第 2、4 项都按这个原则做。

## 1. 出口统一过滤

### 1.1 现在的样子

资料离开这台电脑有几条路，各自过滤，规则写在不同的地方：

| 出口 | 去哪 | 现在怎么过滤 |
|---|---|---|
| 远程 MCP（`kaitu mcp --http` 的 remote 工具） | 云端 Agent | 按模块 id 挡财务（`agent-tools.ts:43`、`:208`）；按单个记忆文件的 `sensitive` 挡（`agent-tools.ts:56–77`、`mcp/server.ts:222`） |
| 手机快照 | 手机，经 iCloud 或 GitHub | 投影时只挑需要的字段（`phone-projections.ts`）；一周的「最近变化」用正则匹配版本说明里的「财务、交易、账户、记忆」去掉（`phone-projections.ts:93`）；资料目录只收 `sensitive === false` 的记忆（`:189`） |
| 资料包（「在原来的 AI 里继续」） | 用户粘贴给第三方 AI | 去掉敏感记忆（`handover.ts:381`） |
| GitHub 备份 | 用户自己的私有仓库，**也是云端整理员读写的地方** | 只按文件名挡密钥类文件；记忆、财务明细按「文字 / 记录」开关整份上传（`workspace-backup.ts` 的 `selected`） |
| 同步盘（iCloud、Drive） | 整个工作区 | 不过滤（设计如此，资料本来就放在那） |

### 1.2 问题

1. **同一条规则写了好几遍，写法不一样。** 「财务不出去」一处按模块 id，一处靠投影时不挑，一处靠正则匹配中文词。以后加一个出口（问问的新工具、飞书、手机问问），就要再写一遍，漏一处就是一次泄露。PR #11 修过的「公网读到敏感记忆」就是这类问题。
2. **最近变化靠正则匹配版本说明。** 一条财务记录的版本说明里没出现那几个词（例如「记了一笔 3,200 的午餐」），就会出现在手机的一周近况里。
3. **GitHub 仓库身兼两职。** 它既是完整备份（应该什么都有），又是云端整理员干活的地方（整理员不该看到敏感记忆和财务明细）。远程 MCP 小心地挡掉了这些，GitHub 这条路却全给了。这不是代码错误，而是口径没定。

### 1.3 方案（最小版本）

新建 `packages/core/src/exposure.ts`，一个函数说清「这个文件能不能去这个出口」：

```ts
type Scope = "agent" | "phone" | "share" | "backup";
// agent：云端 Agent、远程 MCP、问问的内置 AI；phone：手机快照；share：资料包；backup：GitHub 备份
export function shareable(ws: Workspace, path: string, scope: Scope): boolean
export function shareableMemories(ws: Workspace, scope: Scope): MemoryEntry[]
```

规则只按**文件**判断，一张表：

| 内容 | agent | phone | share | backup |
|---|---|---|---|---|
| `finance/` 下的明细记录 | 否 | 否（只出汇总） | 否 | 按 1.4 定 |
| `sensitive` 不是明确 false 的记忆 | 否 | 否 | 否 | 按 1.4 定 |
| `.kaitu/`、密钥类文件名 | 否 | 否 | 否 | 否 |
| 其他 | 是 | 是 | 是 | 是 |

然后把上表各出口的过滤都换成调用它：

- `agent-tools.ts` 的 `read_file` / `record_list` 边界；
- `mcp/server.ts:222`；
- `handover.ts:381`；
- `phone-projections.ts` 的资料目录；
- `workspace-backup.ts` 的 `selected`（按 1.4 的口径）。

「最近变化」不再匹配版本说明的文字，改成看这个版本改了哪些文件，用 `shareable(path, "phone")` 判断，只要有一个文件不能出去，这一条就不显示。

不做报告里的「污点追踪、双标签、脱敏证明」：那套要给每条数据和每个派生结果打标签、在类型层传播，对一个本地文件夹应用太重。实际的边界就在文件这一层，按文件判断已经覆盖了现在所有的出口。整理员写的每日整理如果提到了财务，那是 Agent 读到之后写的，标签也拦不住；这一点靠「agent 出口本来就不给财务明细」解决。

### 1.4 要用户定的口径

GitHub 备份里放不放敏感记忆和财务明细？

- **A. 放（现状）**：备份完整；但云端整理员能读到。设置页要明说「整理员能读到仓库里的全部内容，包括财务和敏感记忆」。
- **B. 不放**：备份不完整，这两类只在本机和同步盘里；整理员和远程 MCP 看到的范围一致。

建议 B：开图对用户说的是「敏感的只在这台电脑上」，而 GitHub 仓库现在实际是给 Agent 读的。

### 1.5 验收

- 一个表格驱动的测试：合成工作区里放带 `PRIVATE_` 标记的财务记录和敏感记忆，逐个出口生成内容，断言里面没有 `PRIVATE_`。沿用 `phone-sync.test.ts` 现有的做法。
- 一条版本说明里不含任何关键词的财务改动，不出现在手机的一周近况里。

## 2. 趋势体重

### 2.1 现在的样子

今天页和一周近况里的「体重 71.6 kg」是**最近一次称重**（`overview-page.ts:123–125` 取最后一条 `kind: weight`）。人一天之内体重能差 0.5–1.5 kg（水、盐、碳水、排便），所以这个数字今天高明天低，看不出走向，用户容易因为一次称重高了就泄气。

### 2.2 方案

一个纯函数，按时间间隔做指数平滑：

```ts
// τ = 7 天；两次称重间隔越久，新读数的权重越大
trend = previous + (1 - Math.exp(-days / 7)) * (reading - previous)
```

- 同一天多次称重取当天第一次（通常是早上），单位统一成 kg。
- 输出：趋势值、和 7 天前趋势的差、最近 14 天的称重次数。
- 最近 14 天少于 3 次称重：不显示趋势，只显示原始读数。超过 21 天没称：从下一次称重重新开始。
- 显示成「71.6 kg · 趋势 72.1，这周 −0.3」。用词是「趋势」，不说「真实体重」，也不推算代谢或「预计哪天到多少」。

### 2.3 范围

- 约 40 行加 3 个测试（等间隔、不规则间隔、称重太少），放在 core，健康页和今天页共用。
- 先只在电脑上显示，不改格式。要进手机的一周近况，需要在 `phone-week.schema.json` 的 `health.weight` 加可选字段 `trend`、`change_7d`，属于数据规范改动，单独确认。
- 不做 TDEE 反推：它要求每天都记热量，首批用户（求职、学语言、写作）大多不记饮食。等健康类用户多了再看。

## 3. 记忆的「已结束 / 被替换」

### 3.1 现在的样子

记忆是 `memory/<type>_<slug>.md` 一个文件一条，frontmatter 有 `type`、`name`、`text`、`created`、`updated`、`sensitive`（`schemas/memory.schema.json`）。改一条记忆就是改这个文件；旧内容只留在版本历史里，AI 的工具读不到，`MEMORY.md` 索引也只列现在的内容（`memory.ts:212`）。

### 3.2 问题

- 偏好会变：「早上训练」变成「晚上训练」，「在 A 公司」变成「离职做独立项目」。直接覆盖以后，AI 不知道以前是什么、什么时候变的，也就答不了「我当时为什么那么定」。这正好对应定位里的「几天前、几个月前的建议还找得到」。
- 不覆盖、另写一条的话，新旧两条同时在索引里，AI 会拿到互相矛盾的说法。
- 过时的记忆没有退场的办法，只能删；删了就彻底没了。

### 3.3 方案（最小版本）

记忆 frontmatter 加两个可选字段：

```yaml
ended: 2026-11-02         # 这条从哪天起不再成立
replaced_by: context_indie-project.md   # 可选，被哪一条替换
```

- 没有 `ended` 的是「现在的」：`MEMORY.md`、Agent 读到的记忆、手机资料目录只列现在的。
- 有 `ended` 的是「以前的」：文件留着，用 `read_file` 能读；电脑上「我的 › 记忆」里折叠成「以前」一栏。
- 谁来标：
  - 用户在界面上点「这条不再成立」，或改写时选「替换成新的一条」。
  - AI 只能**提议**：收件箱的记忆候选加一个可选 `replaces: <文件名>`。用户确认后，新的一条写入，旧的一条加上 `ended` 和 `replaced_by`。AI 不能直接给已有记忆标结束，和「AI 的建议不被记成用户的决定」一致。

不用报告里的「双时态」两条时间轴：「什么时候成立」用 `created` 和 `ended` 就够了；「系统什么时候知道的」已经有版本历史。也不做图谱、PageRank 和自动衰减：个人记忆是几十到几百条，按类型列表加全文搜索就够了；自动衰减会让系统替用户判断「这条不重要了」。

### 3.4 范围

改 `schemas/memory.schema.json`、`memory.ts`（列表和索引过滤）、`agent-tools.ts`、资料目录、收件箱记忆候选格式、AGENTS.md 生成模板、「我的 › 记忆」界面，加测试。属于 PRD §6 数据规范改动，**等用户确认后再做**。

### 3.5 验收

- 一条记忆被替换后：`MEMORY.md` 只有新的；`read_file` 能读到旧的，旧的带 `ended` 和 `replaced_by`。
- Agent 交来带 `replaces` 的候选：用户确认前，两条记忆都不变。

## 4. 夜间整理多做三件事

### 4.1 现在的样子

整理员夜里按 `ORGANIZER.md`「夜里：每日整理」做七步：合并交接进各模块的下一步，把原文整理成待核对草稿，写每日整理（昨天做了什么、当前下一步、原文整理、未决事项、收件箱里还没导入的记录），归档交接。它做的基本是搬运和归档。

### 4.2 问题

四道门槛里的 G2（第二天接得上）和 G4（值得反复打开的页面）需要的东西，夜里没人做：

- 「这个项目这周推进了什么」没有人写；
- 一条下一步挂了十天没动，没有人提；
- 白天聊出来的想法和新说法，跟已有记忆对不上，也没有人发现。

报告说的「睡眠期巩固」方向是对的，但不需要新架构，是规则和输出的升级。

### 4.3 方案

每日整理加三节，**全部是建议，不改任何资料**：

1. **这周推进了什么**：每个进行中的项目和目标一两句，附来源文件。这一节周日写，平时不写。
2. **卡住的下一步**：超过 7 天没动的下一步，每条给三个选项「继续 / 拆小 / 不做了」，由用户在开图里点。
3. **可能要更新的记忆**：这两天的交接和原文里，和现有记忆说法不一致的地方，列成「原来：… / 现在：…」，用户确认后按第 3 项替换。

**数字由代码算，AI 只写话**：

- 新增 `kaitu organizer facts --json`，给出这周每个项目的记录数和字数或提交数（和手机 `week.json` 同一套算法）、超过 7 天没动的下一步（看 STATUS.md 的 `updated` 和下一步的 id）、最近两天改过的记忆。
- 整理员读这个结果再写这三节，不自己去数 JSONL。没有命令行的云端整理员读手机的 `week.json`，效果一样。
- 规则版本从 1 升到 2（`generator.spec` 跟着变）。电脑自带的「开图每日整理」和云端整理员用同一份规则。

### 4.4 验收

合成工作区里放一条 10 天前的下一步，和一条与现有记忆矛盾的原文。跑一次夜间整理后，每日整理里两样都被列出；除了每日整理和归档的交接，没有任何文件被改。

## 暂不引入的部分

| 提议 | 原因 |
|---|---|
| 动态 TDEE | 要求每天记热量，首批用户大多不记；MacroFactor 的壁垒是记录体验和用户数据，不是公式 |
| 训练准备度（Banister） | 要连续的训练量和 RPE，还要按个人拟合参数；套通用常数会得到看起来精确的错数；还有健康类声明的审核风险 |
| 双时态图谱 + PageRank | 个人数据量下全文搜索加文件结构够用；多一套图谱要维护抽取质量，出错不容易被发现 |
| 技能自演化（WikiSkill） | 每周的建议只有几条，采纳率信号太稀太噪，验证门在统计上不成立；还会把系统优化成「说用户爱听的」，和「该你定的留给你」冲突。适合当研究项目，用自己的数据做实验 |
| 潘多拉魔盒指数 | 要用户给每个方向填期望、方差和探索成本，普通人填不出来，算出来是伪精确；「迷雾、探图」可以留作文案和视觉 |
| 信念依赖图 + 多模型 Brier 校准 | 用户不会维护命题和证据；Brier 需要大量有结果的预测记录 |
| 因果扫描 | 两个月数据、几十个变量两两比较，必然冒出假相关；和 2026-10-17 的决定冲突 |
| 节律调度 / 主动干预 | 违反「不催」；要通知基础设施；误报的代价高 |

等 10 人试用跑完两周、知道大家为什么回来以后，再从这张表里挑。
