## 2. 测量边界

- “首次”指新进程 / 新 Workspace 的首次请求；OS 文件页缓存没有清空，不称磁盘冷态。HTTP 热态为首次读取之后的 5 次，表中为中位数 / 最大值。
- HTTP 数字从发请求到完整响应体读取并让出一次事件循环。5 ms 定时器观察最大间隔；它是局部观察值，不是全局上界。CLI 数字是完整新子进程耗时；其 JSON 中的间隔是父进程观察值，不能拿来证明 CLI 子进程不阻塞。
- 浏览器反馈为 pointerdown 后第一次 DOM 变化再跨两帧；内容完成时间由浏览器内 MutationObserver 和两帧记录，避免服务端同步计算拖晚自动化驱动取样。`driverObservedMs` 仅保留作对照。恢复可操作另看 `readyForNextMs`。
- 今天 / 资料热切换可以显示已有数据；表中明确缓存状态。它不代表最新后台刷新已经结束。首次导航数据与“模块载入后的服务构造时间”分列，未把二者冒充原生 App 的完整冷启动。
- 后台完整结束使用正常 2 秒调度，等待真实 Git 版本包含写入内容。100 条记忆和 100 个对话文件均核对完整集合及每个实际文件的 Git blob 字节身份。HTTP 脚本里的 `*-full-snapshot-drain` 是主动排空的执行成本，**不当作正常调度的结束时间**。
- 本轮没有 AI、日历、GitHub 备份或云盘网络请求。以下超时均为本地启动、文件、索引、监听或版本保存成本，未归到“外部等待”以排除预算。

## 5. Profiler 根因与改动

### 健康投影

精确 #59 的 [CPU profile](perf-2026-10-20/evidence/pr59/health.cpuprofile) 覆盖 5 次健康读取，采样总计 1012.9 ms；其中构造每个训练 session 的 map 为 344.5 ms（34.0%）。旧实现把两年前的训练也换算日期、分组并构造 exercises，最终所有返回视图只消费上月、本月、近 30 天及近 5 周。

V2 在 `readWorkbench` **完整折叠修订后**，按所有返回视图中最早的当地日期筛选投影输入；先用 UTC−14h 的安全粗界筛除远期旧记录，再按真实时区判断。没有截断记录读取、删除历史或改数据格式。[叠加后的 profile](perf-2026-10-20/evidence/pr59-v2/health.cpuprofile) 总计 590.5 ms，`readHealthPage` inclusive 为 513.5 ms，之前为 905.3 ms；剩余主要在原有 workbench / 项目读取。采样比例不能当成确定性耗时上界。

五组完整健康响应 SHA-256 均为 `f0cbee9e4a8e21dcdf0198803fbef015900c5d002c6e825c5755d8ab5b238838`。新增一项行为回归覆盖 UTC+14 / 洛杉矶、月界、热力图界、跨月修订、删除和未来记录，不靠伪造系统时间或只断言常量。

### 浏览器写后重复刷新

写入显式 `run → refresh`、立即订阅通知、随后文件监听通知会并行触发整组读取；旧 sequence 只丢弃旧结果，没有取消已发出的计算。[浏览器请求时间线](perf-2026-10-20/evidence/pr59/browser.json) 中，一次完成在采样窗口内有 16 个请求（写入 + 三组各 5 项读取）。叠加后同一写入返回窗口为 6 个（写入 + 一组）；main 上仍可能有完整读取结束后的必要补读。

V2 仅在本机写入进行期间合并订阅通知。写后读取开始前的通知由这次读取覆盖；读取期间再来的变化保留 pending，结束后补读。没有屏蔽文件监听或丢掉外部改动。两个 V2 浏览器旅程都用真实文件编辑配合暂缓读取响应，验证外部修改最终出现在页面；捕获与完成也核对实际文件。main 仍保留 #58 已处理的无关资料读取，未复制该 PR 的实现。

### 首轮文件导入剩余根因（后续修复见 §8）

精确 #59 的 [导入 CPU profile](perf-2026-10-20/evidence/pr59/file-import.cpuprofile) 采样 1705.5 ms，其中 1055.5 ms（61.9%）在 Node Linux `recursive_watch` 的文件事件处理，约 830.8 ms 进入 `#watchFolder`；随后 `refreshOverview` 为 322.6 ms（18.9%）。新增批量文件时的递归监听遍历 / stat / path 处理是此环境的主要剩余阻塞，不能直接套用于 macOS 原生监听或 iPhone。

本轮未强制改用平台轮询、关闭监听、提高 timeout 或删除全量盘点。该项保留为未达标问题；可据此单独评审 Linux 批量写入时的监听调度，Mac 阶段核对实际宿主是否存在同一成本。已有 #59 导出完整性、取消和恢复测试不重复，独立 QA 依据见 [既有评论](https://github.com/Stahl-G/rensheng-kaitu/pull/59#issuecomment-6274039737)。

## 8. 持续收口：监听遍历与版本索引

本节对照为 #60 原 head `5b0bc1e808c80a375da28e249aa550e06b2ee284` 与后续相同分支，不再拿 main 当作这一轮的修复前状态；沿用同一个已校验的合成夹具，全部串行。`watch` 中间因果对照只替换监听，`final` 再加批量暂存。原始数据在 [followup](perf-2026-10-20/evidence/followup/)。

### 门槛与用户影响

AGENTS.md 第 5 条仍是日常反馈 100 ms、返回 300 ms；一次性重活 1 秒并立即显示进度，做不到写明原因。存版本是明确要求后台执行的慢活，但**本地后台成本不能伪装成外部等待，也不能不报完整结束时间**。约 3 秒由原有约 2 秒的合并窗口和其后完整盘点 / Git 提交组成；本轮不改这个窗口或其他超时阈值。

导入时原有 Node Linux 递归监听先遍历全部内部目录，再在回调中忽略历史 / 缓存，因此回调过滤无法避免底层遍历成本。后续复用锁文件中已有的 Chokidar 5.0.0，将同一 `ignoredWorkspaceChange` 规则前移到遍历阶段；两处工作区监听都走同一 19 行函数。显式增加该直接依赖，没有新增解析版本、任务框架、Linux 特例或持久缓存。初始异步监听 ready 后补一次失效，保留初始化期间的外部变化；监听失败的完整轮询路径仍保留。

版本保存仍调用完整 `statusMatrix`，但原实现每新增一个文件都调用一次 `git.add`，重复解析和写整份索引。现使用现有库的多路径 API：新增文件每批最多 32 个，避免库内部同时打开无限多个文件；删除集合仍完整暂存。Git cache 只在这一次保存内部共享，下一次完整盘点重新建立，未缓存掉工作区校验或外部变化。32 是文件句柄并发界限，不是修改性能门槛。

**没有前台固定 300 / 500 ms 的 debounce 可删。** 写响应后约 0 ms 就刷新，最后两帧只占约 13–18 ms。单支同时发 overview、calendar、完整 library、me、onboarding、calendarPush 六项，整组完成才 setData；服务端的同步读取会让并行 HTTP 在同一 Node 主线程排队。独立未加 profiler 分段中，完整 library 占约 106 ms，onboarding 约 101 ms；overview 等异步历史读取时，也受这些同步工作影响。另有文件监听的 300 ms 后台现状刷新竞争本地 CPU，不能把它误当 UI 人为等待，也不能称为外部网络等待。

真实 CPU profile（单独串行运行，不用其数字替代上表）在“记一条 → 完成 → 健康”旅程累计采到 readWorkbench inclusive 1077.3 ms、readLibrary 393.4 ms、onboardingStatus 401.1 ms、refreshOverview 288.0 ms。这些跨多次调用，互相可重叠，不能相加当单次耗时。一次早期探索 profile 与构建重叠，已明确排除，保留的是串行替代文件。

可安全删除的“今天页完整资料读取 / 整组结果门控”已在 #58 实现。精确 #59 含它，临时组合不再发该 library 请求，并保留 V2 的写后通知合并，最终 285.2 ms；没有把 #58/#59 的提交复制进本 PR。再直接删掉文件监听后的补读会丢外部编辑，这不是安全的数字优化。本项以**单支仍约 513 ms、组合样本约 285 ms、修复责任已在 #58**结束，不再发明缓存或改功能。

## 13. 原文保存失败后的待存意图与真实恢复

独立复核发现上一修复只保证正常原文会存版本，失败后先清空 messages 仍会漏掉恢复。新回归在原 `ea35cea` 上真实复现：前两条正常 HTTP 原文已读回 Git，第三条对象目录只读后正文保留，但恢复权限定时重试仍读不到 Git。失败日志见 [checks.json](perf-2026-10-20/evidence/render-retry/checks.json)。

最小修复在已知降级失败和未知异常时都保留本轮保存意图，未知异常继续抛出；没有再次调用 capture 或重写正文。完整 statusMatrix 的现有结果额外提供“是否还有包含 inbox 的真实待存文件”，用于区别失败和原文已经被前一版本收录的合法 no-op；无新增文件扫描、缓存或全局锁。只有真实提交成功，或完整盘点证实已无待存内容时才清掉这一轮意图。默认调度 2 秒 / 重试 30 秒不变。

Linux 非 root 的独立 [raw-note-retry.mjs](perf-2026-10-20/raw-note-retry.mjs) 使用产品默认值：对真实 blob 对象目录 chmod 只读，观察到真实 EACCES，确认 HEAD 未前进且正文未变；恢复后定时重试 **30025.8 ms** 读回完整 blob；另一次失败恢复后关闭 UI，**46.1 ms** 完成真实 Git 回读。每条原文只有一份，未重复写入。原始异常记录含底层库首次写入时可自行恢复的 ENOENT，不把这些内部重试误作被业务吞掉的未知终态错误；两个故障阶段均明确观察到目标路径 EACCES。该权限 / 关闭验证使用小合成资料，不拿 46 ms 当大资料的性能结论。

UI 与历史两个相关文件 **16/16 通过**，覆盖定时重试、关闭补存、合法 no-op、未知错误继续抛出和实际 blob 字节；未增加测试数量、skip 或超时。core / CLI build、typecheck 通过。Windows 没有 POSIX 目录权限语义，不冒充在该平台执行本故障注入；其正常 HTTP / Git 原文旅程仍保留。按父线程要求未重跑无关本地全量项目，自动 CI 按新 head 另记。

## 14. Git 回读与并发覆盖的证据更正

旧 overlap 脚本逐条读取的确实只有 11 份原文；之前回复所述 11 个完成状态另有本地补读，但未归档脚本 / 原文结果，因此不能由旧脚本单独证明。现已将校验写入 overlap.mjs：从同一真实版本读取每个 STATUS.md，解析 next 并要求对应 id 的 status=done，再保存逐份实际 blob 文本。本轮原始结果包含 **11 份原文及 11 份完成状态** 的真实回读。

旧样本最大 HTTP 响应是 **206.4 ms**，此前回复的严格“≤206 ms”措辞有误。本轮相同规模、绑定完整补丁的新增样本最大为 **289.2 ms**；不是稳定上界，也不是 p95，两个样本都保留，未挑较快值。

覆盖边界也已写入脚本和 [overlap.json](perf-2026-10-20/evidence/render-retry/overlap.json)：以首请求为 t0，本轮所有请求在 **t=3611.6 ms** 结束；首次保存 **t=2159.9–4337.9 ms**，只重叠其中 **1451.7 ms**；第二次保存 **t=4633.5–5940.4 ms**，与请求不重叠。`fullSaveCovered` 两项均为 false。故只能说观察到第一次保存中段的前台响应；**没有覆盖两次保存全程**，最终 Git 回读也不能替代全过程的前台响应测量。
