## 通过的实际结果

- 产品连接确认私库；空仓库首次上传、真实 GitHub 回读成功。
- 凭据、媒体和合成用户 `.git` 指针没有上传，原指针保持原样。
- 从远端恢复到第二个隔离工作区；A 改档案、B 改规则，两端往返一致。
- 不同记录的并发新增成功合并。
- 同一记录在 A 跨月份修改、B 删除，产生记录冲突并保留双方；选择 B 的删除后，两端同步一致。
- 正常删除文件后远端也删除；再次恢复到全新工作区，资料与已解决的记录一致。
- 模拟 iCloud 占位后，在任何 GitHub 请求前暂停本轮，没有上传删除。
- 普通同步没有重复查询仓库可见性。真实请求 136 次，除空仓库预期的首次 409 外，没有接口错误。

测试完成后保留私库和合成工作区，不删除仓库，不合并 / 发布，不更新日常安装。

## 认证覆盖边界

复用本机已有 `gh` 登录，以测试进程内的 HTTP 转发调用 `gh api`；没有提取 / 打印 token，没有创建新的永久凭据。转发只接受 `Stahl-G/kaitu-sync-test` 的 GitHub API 路径，服务端返回均来自真实 GitHub，没有 mock 响应。

产品的请求构造、响应解析、Git 对象与引用更新、缓存、同步、冲突和恢复路径均被实际执行。这个转发器只用于验收，不是产品可选的认证入口；产品当前从本机 secrets 读取 token、由原生 fetch 发出认证请求的链路没有在本轮测。因此结果是“真实 GitHub 数据往返通过”，不宣称产品原生认证的完整端到端通过。
