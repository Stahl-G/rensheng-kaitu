# 手机同步电脑端 D1–D3 验收

分支：`feat/phone-sync`。范围：架构交接 §3.B；不含照片、数据规范 A、iOS、发布或真实 GitHub 连接。

## 已实现

- 进度行与足迹路线移入浏览器可用的 core 子路径，插件复用相同实现。
- today / week / map 纯投影，后台两秒防抖生成，内容不变不写，只有同步存放位置或启用 GitHub 时生成读快照。
- phone 不作为模块、不进本机历史，Agent 写入策略拒绝改写；Host / Origin 和 MCP 策略保留。
- GitHub 手机四份快照只上传，agents 文本与 health JSON 入箱始终同步，不受备份内容开关影响；处理完删除远端原件。
- 手机原文保留 capture、作者和日期，origin 映射记录作者。四种操作核对当前前提并按 client_id 去重。
- 最近十四天回执独立于本机操作账本，重启和回执过期不影响去重；冲突原因显示在今天页。
- 本周原文统计包含已归档 capture。快照不复制原文、项目链接、记忆、财务明细或凭据。
- 契约说明与 PRD §6、GitHub 说明、AGENTS 生成模板已同步；模板生成版本递增至 3。

## 合成往返

自动验证覆盖：快照 schema、项目和健康非空投影、跨日期变更线计划路线、生成目录策略与历史排除；
手机原文保留和归档计数、混合 origin 记录、四种操作的实际状态变化、预留操作拒绝、过期前提冲突、跨重开去重；
本地 GitHub 模拟的快照上传、远端快照不能覆盖本机、手机原文与健康入箱拉取、处理后远端删除和回执上传。

## 大工作区实测

命令：构建后运行 `node scripts/measure-phone-sync.mjs`。Node 26.11.1，macOS，合成 300 项目、20,000 条记录、2,000 篇原文。
记录分布：19,900 条训练与 100 条待办。100 条操作为 complete_task；四种操作的组合由行为测试覆盖。

| 项目 | 实测 | 目标 |
|---|---:|---:|
| buildPhoneToday + Week + Map（已读数据） | 0.868 ms | ≤150 ms |
| today.json（实际写入格式） | 980 字节 | ≤65,536 字节 |
| map.json（实际写入格式） | 64,098 字节 | ≤262,144 字节 |
| week.json | 302,015 字节 | 无规定上限 |
| 内容未变的 writePhoneSnapshots | 0 次写入 | 0 |
| 100 条手机操作（processInbox） | 225.887 ms，100 条 applied | ≤500 ms |
| 重投同 client_id | 0 条新增修订 | 只执行一次 |
| 资料变更至快照落盘 | 5,714.917 ms | 防抖 ≥2,000 ms |

落盘时间主要花在 readOverviewPage 读取聚合现有项目、原文和健康读数。week.json 随项目数线性增长（300 项目 × 7 天）。
初测 100 操作 674.572 ms，去掉批内重复读取待办清单后，上表复测达标。
