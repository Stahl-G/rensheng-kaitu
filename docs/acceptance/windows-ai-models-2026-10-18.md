# Windows 模型选择修复（本地，未发布）

用户反馈：Key 已填入，服务返回「2 个模型」，但弹出列表中的模型无法点选，连接流程无法继续。

## 原因与修正

此前开图的连接弹窗使用 `input + datalist`，模型来自服务端，弹出列表由 Chromium / Electron 的自动填充菜单绘制。Windows 原生窗口中实际点击已显示的模型项，输入框仍空、下一步仍禁用，复现了用户问题。它是开图共用页面中的控件，并非 DSH 的服务商接口失败。

- 所有厂商共用标准 `select` 模型选择框，获取后保留仍可用的当前型号，否则选择第一个返回型号；不写死模型名单。
- 下拉框提供手动填写入口，继续支持服务没有返回的模型 ID。
- 移除 Key 失焦时自动请求，使用明确的获取按钮；获取期间不禁用 Key、服务商与接口编辑。
- Key、厂商、协议或 Base URL 改变后，使之前的模型请求失效；旧响应不会覆盖新选择。
- Mac / Windows 保持同一个组件、接口、DSH 引擎和 npm 后端，无独立 Windows 模型实现。

## 已验证

- 使用用户提供的 Key 访问 DeepSeek 官方模型接口，返回 `deepseek-flash` 和 `deepseek-v4-pro`，最小连接验证成功。没有发送用户资料或真实聊天请求。
- 通过本机已安装 Windows EXE 的 `/api/product/askModels`，HTTP 200，返回上述两个模型及图片能力。
- 通过同一应用的连接接口，HTTP 200、`configured: true`，DeepSeek / `deepseek-flash`。Key 交给原有本机凭据存储，没有写入源码、文档、安装包或接口响应。
- 对真实 AskPage 组件执行两组代码交互回归：Key 输入、模型获取、两个型号切换、手填、提交；切换厂商、其他厂商型号选择、请求中编辑 Key、拒绝过期响应、失败后修改 Key 并重试。使用合成网络结果和临时 React renderer，两组均通过。
- 客户端构建、全仓类型检查、lint 通过；本机安装目录中的前端资源已替换，构建源与安装目录的 JS SHA-256 一致。
- 本机应用重启后，通过新服务端口读取设置仍为 `configured: true`，只使用本机已保存凭据获取模型成功；新进程提供的前端资源与修复后构建哈希一致。

用户随后要求回到代码处理，因此修复后未继续做 Computer Use 点击验收。其他厂商的控件行为经过合成响应测试，没有其他厂商的真实 Key，不能据此宣称所有服务的联网授权均已验证。
